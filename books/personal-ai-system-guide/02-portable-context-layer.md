# 全体設計 ― portable context layer という考え方

Personal AI Systemの中心は、特定ツールの組み込み記憶ではなく、portable context layerです。これは、エージェントやモデルが変わっても持ち運べる、ファイルベースのコンテキスト層を意味します。Markdownを中心に、正本、索引、運用ルール、ワークフローをリポジトリへ置きます。

## なぜ組み込み記憶だけに依存しないのか

組み込み記憶は手軽ですが、何が保存され、いつ更新され、どの情報を根拠に回答したのかを利用者が完全には追跡できないことがあります。ツールを切り替えたときに移行しにくく、古い情報を削除・訂正する単位も曖昧になりがちです。さらに、保存された事実とその場の推論が混ざると、誤りが次の回答へ連鎖します。

ファイルを正本にすると、差分を確認でき、バックアップや検索ができ、別のエージェントにも同じ前提を渡せます。人間が直接編集できることも重要です。AIの記録が間違っていたとき、利用者がその場で正しい表現へ直せます。

## 4層で考える

設計は次の4層に分けると安定します。

1. **データ層**: プロフィール、目標、制約、プロジェクトなどの事実。
2. **正本・索引層**: どの事実をどのファイルで管理するかを示すマップ。
3. **指示層**: エージェントの応答スタイル、事実ラベル、検証ルール。
4. **実行層**: セッション開始、記憶メンテナンス、日次ブリーフなどの手順。

データ層だけを増やしても、正本がなければ重複します。指示層だけを詳細にしても、参照する事実がなければ一般論になります。4層を分離し、リンクで接続するのがポイントです。

## 正本とキャッシュを分ける

正本は、その事実を更新する唯一の場所です。例えば、今期の目標は`context/goals.md`、回答の好みは`context/preferences.md`と決めます。日次ブリーフやプロジェクトメモには、正本の全文を複製せず、その時点の要約とリンクだけを書きます。要約を更新し忘れても、AIは正本へ戻れます。

一方、メールの検索結果やツールの出力は、観測時点のキャッシュです。取得日と出典を付け、変動し得る情報には「要再確認」を付けます。キャッシュを正本と呼ばないことが、記憶汚染を防ぎます。

## 最初から個人情報を全部入れない

秘書化を急ぐと、プロフィール、履歴、購入記録、第三者の情報を一度に投入したくなります。しかし、情報量と有用性は比例しません。まずは回答の好み、現在の目標、判断上の制約、進行中の案件だけで十分です。認証情報、秘密鍵、金融原本、第三者の識別情報は、リポジトリへ保存しません。

この設計なら、Claude Codeで編集し、Codexで監査し、別のエージェントで日次ブリーフを生成することもできます。ツールは交換可能で、正本は利用者の手元に残ります。

## portableであることの実務的な意味

portableとは、単に別のツールでファイルを開けるという意味ではありません。エージェントの名称やプロンプトの癖に依存せず、第三者が読んでも意味が分かることが重要です。例えば「前回と同じで」と書かれたメモは、会話履歴がなければ利用できません。「2026年7月1日、朝の集中作業を優先する方針を確認済み」と書けば、別セッションでも参照できます。

正本には、事実だけでなく境界も記録します。何を共有してよいか、どの情報が古いか、誰が更新したかを残すと、別のエージェントが安全側へ判断できます。外部サービスの取得結果を保存する場合は、URL、確認日、取得範囲を添えます。将来仕様が変わっても、当時の観測と現在の確認を区別できます。

また、portable context layerはバックアップ戦略とも相性がよい設計です。テキストの差分を確認できるため、不要な変更を戻しやすく、必要な部分だけを別の環境へ移せます。ただし、Gitに置けることと公開してよいことは別です。共有前提の監査、秘密情報の除外、第三者データの匿名化を、移植の前提条件にしてください。

導入時は「どのエージェントでも同じ結果を返す」ことを目標にしすぎないでください。モデル、ツール、接続先が違えば、表現や検索結果は変わります。再現すべきなのは、正本の読み方、確度の扱い、停止条件、検証の手順です。出力の完全一致ではなく、重要な前提と安全境界が一致しているかを評価します。

この評価をすると、モデルを交換するときも移行範囲が明確になります。プロンプトの言い回しではなく、正本、ラベル、検証手順を移せばよいからです。将来のツール変更を特別な引っ越し作業にしないことが、portable context layerの長期的な価値です。

人間が読んで意味を説明できることが、移植性を測る最初のテストです。正本、ラベル、出典、検証手順が独立していれば、モデルやツールを変更しても長期コンテキストを引き継げます。説明できない記録は、まだ正本として扱わず、内容と出典を整理してから採用します。
